# Eval 结果分析报告

## 1. 结论摘要

本次评测可以分成两个层面看：

1. `retrieval` 侧，`bge` 是当前最稳、最强的 embedding 方案；`qwen304b` 次之；`qwen4b` 的 dense 检索出现了明显异常，不像是正常的模型能力差距，更像是索引、向量维度、归一化或查询侧配置失配。
2. `generation` 侧，`bge + qwen2.5-14b` 是当前综合最优方案，`qwen3-0.4b + qwen2.5-14b` 非常接近但略弱；`qwen304b + huatuo`因模型配置问题未能测得正确结果。
3. 当前系统的主要短板已经不是“答不出来”，而是“答得不够完整、不够稳妥”，尤其体现在红旗症状提醒、分诊提示、以及部分问答的完整性上。

## 2. 数据、模型测试范围

- 测试emb模型：`bge-m3` 、`qwen304b（Qwen3-Embedding-0.6B）` 、`qwen4b（Qwen3-Embedding-4B）`
- 测试llm生成模型：`qwen2.5-14b` 、`huatuo` 、`qwen3-14b（后因服务器GPU驱动版本不支持暂无法测试）`

## 3. Retrieval 分析

### 3.1 核心指标对比


| Embedding 方案 | 检索方式   | Recall@5 | Recall@10 | MRR    | P50 延迟  |
| ------------ | ------ | -------- | --------- | ------ | ------- |
| `bge`        | dense  | 96.15%   | 98.26%    | 0.8200 | 51.0 ms |
| `bge`        | sparse | 75.39%   | 83.18%    | 0.6217 | 7.8 ms  |
| `bge`        | hybrid | 93.25%   | 98.17%    | 0.8050 | 47.2 ms |
| `qwen304b`   | dense  | 93.67%   | 96.84%    | 0.7908 | 54.9 ms |
| `qwen304b`   | sparse | 75.39%   | 83.18%    | 0.6216 | 6.4 ms  |
| `qwen304b`   | hybrid | 92.22%   | 97.10%    | 0.7975 | 51.4 ms |
| `qwen4b`     | dense  | 0.00%    | 0.00%     | 0.0000 | 61.2 ms |
| `qwen4b`     | sparse | 75.39%   | 83.18%    | 0.6217 | 8.1 ms  |
| `qwen4b`     | hybrid | 68.23%   | 75.39%    | 0.5675 | 59.9 ms |


### 3.2 结果解读

1. `bge dense` 是本轮检索最优解，`Recall@10=98.26%`、`MRR=0.8200`，说明不仅召回高，而且正确文档排位也最好。
2. `qwen304b` 表现可用，和 `bge` 的差距不算特别大，但整体仍落后一档。若只能在这两者间选，优先保留 `bge`。
3. `qwen304b` 上 `hybrid` 比 `dense` 的 `MRR` 略好，说明混合检索对排序有一点补益；但在 `bge` 上，`hybrid` 并没有超过 `dense`。
4. `sparse` 三组结果几乎完全一致，说明 sparse 分支本身是稳定的，问题主要来自 dense embedding 链路。
5. `qwen4b dense` 全指标为 `0`，这不是正常的模型效果波动，基本可以判定为异常状态。更关键的是，`hybrid` 的表现还低于 `sparse`，说明错误 dense 分支不只是“没帮助”，而是在拖累融合结果。

### 3.3 为什么 `hybrid` 会比 `dense` 差

从当前结果看，`hybrid` 比 `dense` 差，并不意味着“混合检索天然更弱”，而更像是当前融合方式和数据分布下的正常现象，主要有两类原因：

1. 测试方法有问题，数据库中的docment加入了原问题，当使用问题去匹配，就更加容易匹配上，导致dense分数虚高。当 dense 分支已经很强时，sparse 分支带来的增益不够大，反而会引入排序扰动。以 `bge` 为例，`dense` 已经达到 `Recall@10=98.26%`、`MRR=0.8200`，说明正确答案通常不但能召回，而且排位已经很靠前。这时再把 `sparse` 结果混进来，能补回来的漏召很少，但会把一些“词面相关、语义上次优”的文档一起抬进前排，于是 `MRR` 和 `Recall@5` 反而轻微下降。
2. 当前 `hybrid` 用的是 Milvus 原生 `hybrid_search + RRFRanker(k=60)`，属于 rank-level 融合，不看各路分数绝对值，只看每一路里的名次。这种做法的优点是简单稳健，但缺点是无法识别“dense 这一轮其实已经明显优于 sparse”，也无法自动压低一条质量较差的分支；只要某个文档在 sparse 路里排得靠前，就会对最终排序产生实质影响。

总结：当前 `hybrid` 混合逻辑更像是在做“两路候选并集后的名次折中”。在 dense 已经足够强时，这种融合很容易把前排排序变差。

### 3.4 对 `qwen4b` 异常的判断

结合失败样本看，`qwen4b dense` 返回的文档与问题语义几乎完全不对齐，且这种现象是系统性的，不是个别问题失手。因此更可能是以下几类工程问题，而不是模型本身“稍弱”：

1. 文档入库和查询时使用了不同 embedding 模型。
2. 向量维度不一致，但流程没有在写入或查询时及时报错。
3. 向量归一化、距离度量或索引参数配置不一致。
4. 查询文本编码、清洗方式或 tokenizer 处理和建库阶段不一致。

### 3.5 Retrieval 建议

1. 线上主检索建议优先使用 `bge dense`。
2. 如果后续需要保留第二套 embedding 方案，建议选择 `qwen304b`，不建议继续使用当前状态的 `qwen4b`。
3. 尽快单独排查 `qwen4b` 的建库模型、查询模型、维度、归一化和相似度配置；这是高优先级阻塞项。



### 3.6 BGE 表现比qwen 0.6b强的原因分析

1. `BGE` 更像“专职检索模型”。它在这个任务上最强的不是单纯语义理解，而是“把正确文档排到前面”的能力。`MRR` 更高就说明这一点，用户真正感知到的 top1/top3 质量会更好。
2. 当前数据形态本身很吃“问答检索”的匹配能力。当前数据明显是医疗问答式数据，query 也跟知识库问句很接近。对这种场景，专门为 retrieval 优化过的模型往往比通用 embedding 更占便宜。

## 4. End-to-End Generation 分析

### 4.1 核心指标对比


| 组合方案                       | Core 6 metric Avg Score | P50 延迟 | P95 延迟  | Safety Warning | Safety Fail | Triage Warning | Triage Fail |
| -------------------------- | ----------------------- | ------ | ------- | -------------- | ----------- | -------------- | ----------- |
| `bge + qwen2.5-14b`        | 11.14                   | 6.50 s | 11.49 s | 42%            | 0%          | 8%             | 0%          |
| `qwen3-0.4b + qwen2.5-14b` | 10.88                   | 6.40 s | 10.45 s | 42%            | 0%          | 14%            | 0%          |
| `qwen304b + huatuo`        | 7.12                    | 2.41 s | 6.18 s  | 56%            | 8%          | 32%            | 26%         |


### 4.2 各维度表现

#### `bge + qwen2.5-14b`

- 最强项：`answer_relevance=2.0`、`context_relevance=2.0`，50 个样本全部相关且引用上下文匹配。
- 稳定项：`medical_correctness=1.98`、`uncertainty_handling=1.98`、`faithfulness=1.78`。
- 主要短板：`answer_completeness=1.4`、`safety=1.58`。
- 风险标签主要集中在：
  - `missing_red_flag_warning = 17`
  - `insufficient_medical_disclaimer = 3`

判断：这是一个“能答对，也能引用，但还不够像临床安全助手”的状态。

#### `qwen3-0.4b + qwen2.5-14b`

- 综合质量和第一名接近，且 `P95` 延迟略低。
- 但它在完整性、忠实性和分诊上都比 `bge + qwen2.5-14b` 稍弱：
  - `answer_completeness=1.3`
  - `faithfulness=1.62`
  - `triage_warning_rate=14%`
- 风险标签分布也更差一些：
  - `insufficient_medical_disclaimer = 7`
  - `missing_red_flag_warning = 15`

判断：这组可以作为候选备份方案，但当前还不是最优主方案。

#### `qwen304b + huatuo`

- huatuo部署失败，未能正常生成
- 可能原因：加载了不匹配的 tokenizer / special tokens、和当前旧版本transform有兼容性问题

### 4.3 Failure 文件怎么理解

需要特别说明：前两组的 failure 文件数量分别有 `38` 和 `41`，并不代表它们“失败率高达 76% / 82%”。结合 summary 看，这些 failure 文件更像是在收集“任何存在 warning 或 fail 的样本”，而不只是硬失败样本。

因此更合理的解读是：

1. `bge + qwen2.5-14b` 和 `qwen3-0.4b + qwen2.5-14b` 的主要问题是 warning 级问题，尤其是完整性和安全提醒不足。

### 4.4 典型问题模式

结合失败样本，当前 generation 结果主要有二类问题：

1. 红旗症状提醒不足。
  例如儿童发热抽搐、妇科异常、急症前兆这类问题，回答虽然方向基本对，但没有稳定补上“哪些情况需要立即就医”。
2. 回答完整性不足。
  很多答案能给出核心结论，但缺少鉴别点、观察点、处理边界或后续步骤，因此被打成 `warning`。

## 5. 综合判断

### 5.1 当前最优方案

如果目标是“可上线的医疗 RAG 助手基线”，当前建议排序如下：

1. `bge + qwen2.5-14b`
2. `qwen3-0.4b + qwen2.5-14b`
3. `qwen304b + huatuo`

### 5.2 为什么首选 `bge + qwen2.5-14b`

1. 检索侧是全场最强。
2. 生成侧综合分最高。
3. 忠实性、分诊、安全性整体优于另一组 `qwen2.5-14b` 组合。
4. 没有出现硬性的 citation 体系失效。

## 6. 后续优化优先级方向

### P0

1. 排查并修复 `qwen4b dense` 检索异常。
2. 给 generation 模板补强强制性红旗提醒逻辑，尤其是儿科、急症、出血、抽搐、胸痛、神经系统症状等场景。
3. 排查并修复 `huatuo` 生成异常。
4. 加入改写query召回测试环节，模拟更加真实的查询环境

### P1

1. 针对 `answer_completeness` 做结构化提示词优化，比如固定输出“结论 / 可以说明 / 不能确定 / 建议 / 何时就医”。
2. 对高风险问题增加分诊优先级规则，减少 `triage warning`。
3. 在生成前增加检索结果质量门控，避免低质量证据被直接喂给模型。

### P2

1. 评估 rerank 是否能进一步提升 `qwen304b` 的 dense/hybrid 上限。
2. 评估在 `bge` 方案下是否有必要保留 hybrid；从当前结果看，dense 已经足够强。
