# 前端架构（第二阶段收口版）

本文档以当前仓库代码为准，描述第二阶段前端已经落地的能力、明确保留的边界，以及不再纳入本阶段的内容。

本阶段的目标已经收口为：

- 提供可用的问答工作台
- 提供最小可用的导入管理台
- 用简单 admin 认证保护导入相关页面和 API
- 用服务端模板和局部刷新完成交互，不引入独立 SPA

不再把“理想态前端平台化能力”继续写进第二阶段范围。

---

## 1. 当前范围

第二阶段当前交付的前端能力包括两块：

1. 问答工作台
2. 导入管理台

它们共享同一套 FastAPI 应用，但身份边界分离：

- 问答工作台使用匿名 `user_token` cookie
- 导入管理台使用独立 `rag_medical_admin_session` cookie

这意味着：

- 普通问答不要求登录
- 导入、进度查看、取消、导入状态查询都要求 admin 认证

---

## 2. 技术实现现状

### 2.1 渲染方式

当前前端不是 SPA，也不是完整的前后端分离。

实际方案是：

- `Jinja2` 服务端模板渲染整页和 HTML 片段
- 模板中使用 `hx-post` / `hx-get` / `hx-delete` 这类属性表达局部交互意图
- `app/web/static/js/chat.js` 用原生 JavaScript 接管这些属性并发起 `fetch`
- 导入进度通过原生 `EventSource` 连接 SSE

所以文档中应将其理解为：

- “服务端模板 + 轻量局部刷新语义”

而不是：

- “完整依赖 htmx 运行时的前端架构”

### 2.2 模块分层

当前前端相关代码主要分布在：

```text
app/
  admin/
    auth.py
    repository.py
  api/
    main.py
  chat/
    repository.py
    service.py
  web/
    routes.py
    templates/
    static/
      css/app.css
      js/chat.js
```

职责边界如下：

- `app/api/main.py`
  - 提供 JSON API
  - 提供 ingest / answer / query / health
  - 在 startup 时做 admin bootstrap 和中断任务收敛
- `app/web/routes.py`
  - 负责页面路由
  - 负责 HTML 片段路由
  - 负责 admin 页面认证跳转
- `app/chat/*`
  - 负责昵称、会话、消息、引用读取
- `app/admin/*`
  - 负责 admin 账号、密码摘要、session cookie

## 3. 页面结构

### 3.1 问答工作台

入口：

- `GET /ui`

当前页面包含：

- 昵称初始化弹层
- 左侧会话侧栏
- 当前会话标题
- `top_k` 选择器
- 问题输入框
- 引用卡片
- 右侧引用详情面板
- “导入工作台”入口

当前行为特点：

- 问答页默认使用 `/answer` 背后的会话编排能力，不直接暴露 `/query` 调试界面
- 用户可以切换历史会话
- 用户可以点击回答中的引用编号或引用卡片查看详情

### 3.2 导入管理台

入口：

- `GET /ui/admin/login`
- `GET /ui/admin/ingest`

当前页面包含：

- admin 登录页
- MongoDB 状态展示
- 导入表单
- 导入任务状态卡
- 失败批次列表
- 既有任务查询框
- 登出按钮

当前导入管理页支持两类操作：

1. 新建导入任务
2. 按 `source_path` 查询当前或最近一次任务状态

## 4. 路由与交互

### 4.1 页面路由

当前已落地的主要页面路由如下：


| 路由                                        | 说明               |
| ----------------------------------------- | ---------------- |
| `GET /ui`                                 | 问答工作台首页          |
| `GET /ui/admin/login`                     | admin 登录页        |
| `POST /ui/admin/login`                    | 提交 admin 登录      |
| `POST /ui/admin/logout`                   | 退出 admin 会话      |
| `GET /ui/admin/ingest`                    | 导入管理台            |
| `POST /ui/admin/ingest`                   | 提交导入表单并返回更新后的管理页 |
| `GET /ui/admin/ingest/status`             | 返回导入状态 HTML 片段   |
| `DELETE /ui/admin/ingest/{ingest_run_id}` | 取消导入并返回状态片段      |


### 4.2 问答片段路由


| 路由                                                                                         | 说明           |
| ------------------------------------------------------------------------------------------ | ------------ |
| `POST /ui/profile`                                                                         | 提交昵称并初始化匿名身份 |
| `POST /ui/conversations`                                                                   | 新建会话         |
| `GET /ui/conversations/{conversation_id}`                                                  | 切换会话         |
| `POST /ui/conversations/{conversation_id}/ask`                                             | 提交问题         |
| `GET /ui/conversations/{conversation_id}/messages/{message_id}/citations/{citation_index}` | 查看引用详情       |


### 4.3 当前前端事件机制

当前前端脚本会处理：

- `hx-post`
- `hx-get`
- `hx-delete`
- 表单 loading / disabled
- SSE 订阅与关闭
- 引用详情面板开关

## 5. 认证边界

### 5.1 问答身份

问答页当前使用临时身份：

- cookie 名：`rag_medical_user_token`
- 用户先设置昵称
- 昵称、会话、消息历史存 MongoDB

### 5.2 admin 身份

导入管理页使用单独的 admin 认证：

- `ADMIN_BOOTSTRAP_USERNAME`
- `ADMIN_BOOTSTRAP_PASSWORD`
- `ADMIN_SESSION_SECRET（签名私钥）`

Mongo 集合：

- `admin_users`

cookie：

- `rag_medical_admin_session`

当前路由规则：

- 未认证访问 `/ui/admin/*` 会跳转到 `/ui/admin/login?next=...`
- 已认证访问登录页会跳回目标页
- admin cookie 是浏览器会话级，不设置长期 `max_age`

### 5.3 受保护接口

当前明确受保护的接口为：

- `POST /ingest`
- `GET /ingest/status`
- `GET /ingest/{ingest_run_id}/events`
- `DELETE /ingest/{ingest_run_id}`
- 除登录页外的所有 `/ui/admin/*`

## 6. 导入任务状态模型

### 6.1 当前前端关注的字段

管理台当前已消费这些状态字段：

- `ingest_run_id`
- `status`
- `stage`
- `execution_outcome`
- `source_path`
- `progress_percent`
- `current_scanned_line`
- `total_lines`
- `processed_batches`
- `succeeded_batches`
- `pending_batches`
- `failed_batches`
- `lines_per_second`
- `batches_per_second`
- `eta_seconds`
- `failed_batch_details`
- `cancel_requested`
- `stale`
- `abandoned`

### 6.2 导入任务显示状态`status`解释

当前页面上，导入任务主要分成三类：

1. 活跃态
  - `queued`
  - `running`
  - `cancelling`
2. 中断态
  - `interrupted`
3. 终态
  - `cancelled`
  - `completed`
  - `completed_with_errors`
  - `failed`

当前实现中：

- 只有活跃态会继续保持 SSE 跟踪
- `interrupted` 不再继续连 SSE
- `abandoned=true` 时页面会提示这是遗留运行态

### 6.3 当前恢复与取消语义

第二阶段当前已经支持：

- 应用启动时会自动把意外关闭进程导致遗留 `queued/running/cancelling` 收敛成 `interrupted`
- 状态读取时把过期 lease 的遗留运行态识别为 stale / abandoned
- 对无 owner 的 `interrupted` 任务直接取消收尾
- 通过同一 `source_path` 查询当前或最近一次任务状态

## 8. 与代码一致的关键说明

为避免文档继续超前，当前应明确以下事实：

1. 当前不是 SPA
2. 当前也不是“严格依赖 htmx 运行时”
3. 当前前端是服务端模板驱动
4. `chat.js` 是局部交互调度器
5. 导入管理页已经不是“只看刚提交的任务”，而是支持按路径找回任务
6. 导入状态模型已经包含 `interrupted / stale / abandoned`

---

## 9. 第二阶段收口结论

如果只以当前项目现状为准，第二阶段可以定义为：

- 问答工作台最小闭环可用
- 管理登录闭环可用
- 导入任务闭环可用
- 进度跟踪闭环可用
- 取消与中断恢复闭环可用
- 文档与实现边界基本对齐

从这个节点开始，后续更适合进入：

- 稳定性修补
- 编码修复与细节清理
- 第三阶段需求再规划

而不是继续扩第二阶段范围。
