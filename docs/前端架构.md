# 第二阶段前端架构设计

本文档面向第二阶段开发，目标是基于当前已经落地的 RAG 后端能力，补齐医疗问答系统的前端页面、交互逻辑和管理端入口。

需求文档中第二阶段范围是“完成前后端主要功能组件”，主要内容为“交互界面逻辑、接口开发”，技术选型为 `jinja2 + htmx`。因此本阶段前端优先采用服务端渲染和局部刷新，不引入重型 SPA 框架。

---

## 1. 阶段目标

### 1.1 核心目标

- 提供中文医疗问答主入口，用户可以输入健康或疾病相关问题。
- 展示 RAG 生成回答、引用来源、检索命中内容和 fallback 状态。
- 支持基础问答会话管理，用户可以在同一浏览器会话中查看多轮提问记录。
- 为数据导入与管理能力增加简单 admin 认证，避免未授权用户直接进入管理页或调用入库动作。
- 提供管理员导入入口，支持提交数据导入任务、查看实时进度、取消任务和定位失败批次。
- 将后端已有的 `/ingest`、`/query`、`/answer`、`/health` 能力封装为可用的页面流程。

### 1.2 本阶段不优先实现

- 完整用户登录、权限、账号体系。
- 多角色 RBAC、组织级权限模型、细粒度资源授权。
- 独立前后端分离构建链路。
- 复杂数据可视化报表。
- 生产级监控大盘。
- 完整评测工作台和模型部署控制台。

---

## 2. 信息架构

第二阶段建议先提供两个主工作区。

### 2.1 问答工作区

面向普通用户或演示验收：

- 问题输入框作为 RAG 搜索主入口。
- 回答结果区展示生成答案、耗时、fallback 状态。
- 引用列表展示 `doc_id`、分数、召回方式相关 metadata 和命中文本摘要。
- 源文档详情区支持点击引用后展开查看完整命中内容。
- 会话侧栏记录当前匿名用户的多会话历史、标题和最近活动时间。

### 2.2 数据管理工作区

面向管理员或开发调试：

- 进入工作区前需先通过简单 admin 登录校验。
- 展示 `/health` 状态，重点显示 MongoDB、Milvus 可用性。
- 提供数据源路径、批次 ID、是否强制新 run 等导入参数表单。
- 提交 `/ingest` 后展示 `ingest_run_id`、状态链接、事件流连接状态。
- 通过 SSE 实时展示 `stage`、`status`、进度百分比、扫描行数、处理速率、ETA。
- 展示成功、待处理、失败批次数，以及 `failed_batch_details`。
- 支持对运行中的导入任务执行取消操作。

### 2.3 身份边界

- 问答工作区保持当前匿名昵称 + `user_token` 会话方式，不引入完整用户系统。
- 管理工作区采用独立 admin session，与问答页匿名会话解耦，避免混用同一 cookie。
- 问答页可以出现“进入导入工作台”入口，但该入口本身受 admin 校验控制。
- 所有入库相关页面路由、htmx 片段路由和 JSON API 都必须做同一层 admin 校验，不能只在页面上隐藏按钮。

## 3. 技术栈

### 3.1 前端技术

- `Jinja2`：服务端渲染页面和 HTML 片段。
- `htmx`：表单提交、局部刷新、加载状态、错误片段替换。
- 原生 `EventSource` 或 htmx SSE 扩展：订阅导入进度流。
- 少量原生 JavaScript：处理 SSE JSON、引用详情切换、会话本地缓存。
- 普通 CSS：先建立稳定、克制、可读的医疗问答工具界面。

### 3.2 后端集成方式

当前 `app/api/main.py` 已经提供 JSON API。前端层建议新增独立 Web 路由，不直接污染核心 API：

```text
app/
  api/
    main.py                 # 现有 JSON API
  web/
    __init__.py
    routes.py               # 页面路由与 htmx 片段路由
    auth.py                 # admin cookie 签名、校验与重定向封装
    view_models.py          # API 响应到模板数据的轻量转换
    templates/
      base.html
      chat.html
      admin_login.html
      admin_ingest.html
      fragments/
        answer_result.html
        citation_list.html
        ingest_status.html
        ingest_error.html
    static/
      css/app.css
      js/ingest_events.js
      js/session_history.js
  chat/
    repository.py           # 历史问答、会话、匿名身份持久化
    service.py              # 会话编排、问题提交、引用回看
```

`web` 层只负责页面表达和交互编排，业务逻辑仍由已有服务与 API 模型承担。

## 4. 页面路由设计

### 4.1 页面路由

| 路由 | 用途 |
|------|------|
| `GET /ui` | 问答工作区首页 |
| `GET /ui/admin/login` | admin 登录页 |
| `GET /ui/admin/ingest` | 数据导入管理页 |
| `POST /ui/admin/login` | 提交 admin 登录表单 |
| `POST /ui/admin/logout` | 退出 admin 会话 |
| `GET /ui/health` | 页面片段：系统健康状态 |

### 4.2 htmx 片段路由

| 路由 | 方法 | 返回 |
|------|------|------|
| `/ui/answer` | POST | 回答结果 HTML 片段 |
| `/ui/query` | POST | 检索结果 HTML 片段 |
| `/ui/citations/{doc_id}` | GET | 引用详情 HTML 片段 |
| `/ui/admin/ingest` | POST | 导入任务已提交 HTML 片段 |
| `/ui/admin/ingest/status` | GET | 导入状态 HTML 片段 |
| `/ui/admin/ingest/{ingest_run_id}` | DELETE | 取消后的状态 HTML 片段 |

当前实际问答页已经落地的核心路由包括：

| 路由 | 方法 | 返回 |
|------|------|------|
| `/ui/profile` | POST | 创建或更新昵称，并写入匿名 `user_token` cookie |
| `/ui/conversations` | POST | 新建会话并刷新问答页 |
| `/ui/conversations/{conversation_id}` | GET | 切换会话并渲染消息区 |
| `/ui/conversations/{conversation_id}/ask` | POST | 提交问题并刷新问答主区 |
| `/ui/conversations/{conversation_id}/messages/{message_id}/citations/{citation_index}` | GET | 渲染引用详情片段 |

### 4.3 admin 认证路由规则

- `GET /ui/admin/login`：未登录时展示登录页；已登录时按 `next` 参数或默认目标跳转到 `/ui/admin/ingest`。
- `POST /ui/admin/login`：校验 `.env` 中配置的 admin 凭证，成功后写入独立 `admin_session` cookie。
- `POST /ui/admin/logout`：清除 `admin_session` cookie，并返回登录页或跳回问答页。
- 访问 `/ui/admin/*` 时，未认证请求统一重定向到 `GET /ui/admin/login?next=...`。
- 问答页里的“入库/导入工作台”入口始终指向 admin 路由，不直接暴露真实入库 API。

### 4.4 SSE 路由复用

导入进度不需要新增后端流式接口，前端直接复用当前 JSON API：

```text
GET /ingest/{ingest_run_id}/events
```

浏览器端由 `EventSource` 订阅，收到 `progress` 事件后更新进度条、指标卡和失败批次表格。

## 5. 当前 API 契约

### 5.1 admin 认证契约

页面层和 API 层都需要共享同一套 admin 校验策略。建议通过独立辅助函数或 FastAPI dependency 统一实现。

建议配置项：

- `ADMIN_USERNAME`
- `ADMIN_PASSWORD`
- `ADMIN_SESSION_SECRET`

建议行为：

- 登录成功后写入 `httponly`、`samesite=lax` 的 admin cookie。
- cookie 内容使用签名或 HMAC，避免前端伪造。
- 页面请求未认证时重定向到登录页。
- JSON API 未认证时返回 `401 Unauthorized`，而不是返回 HTML。

需要受保护的接口范围：

- `GET /ui/admin/login` 之外的所有 `/ui/admin/*`
- `POST /ingest`
- `GET /ingest/status`
- `GET /ingest/{ingest_run_id}/events`
- `DELETE /ingest/{ingest_run_id}`

### 5.2 健康检查

```text
GET /health
```

关键字段：

- `status`
- `project`
- `mongodb`

前端展示规则：

- `mongodb=ok` 时允许提交导入。
- `mongodb=unavailable` 时禁用导入提交按钮，并显示后端不可追踪写入风险。

### 5.3 数据导入

```text
POST /ingest
```

请求字段：

- `source_path`
- `raw_batch_id`
- `clean_batch_id`
- `kb_batch_id`
- `flush_to_milvus`
- `force_reingest`

成功响应为 `202 Accepted`，关键字段：

- `status=queued`
- `ingest_run_id`
- `source_path`
- `status_url`
- `events_url`
- `cancel_url`

前端交互规则：

- 提交成功后立即显示任务卡片。
- 自动连接 `events_url`。
- 同时允许手动刷新 `status_url`。
- `409` 展示为同目标导入正在运行。
- `503` 展示为 MongoDB 不可用。
- `400` 展示为源文件路径或参数错误。
- `401` 展示为 admin 会话失效，并引导重新登录。

### 5.4 导入状态

```text
GET /ingest/status?ingest_run_id=...
```

重点展示字段：

- `status`
- `stage`
- `execution_outcome`
- `progress_percent`
- `current_scanned_line`
- `total_lines`
- `processed_batches`
- `skipped_succeeded_batches`
- `succeeded_batches`
- `pending_batches`
- `failed_batches`
- `lines_per_second`
- `batches_per_second`
- `eta_seconds`
- `failed_batch_details`

状态展示建议：

- `queued`：等待后台任务启动。
- `running`：显示进度条和实时速率。
- `cancelling`：禁用取消按钮，提示正在等待当前批次结束。
- `cancelled`、`completed`、`completed_with_errors`、`failed`：停止 SSE，保留最终状态。

### 5.5 检索

```text
POST /query
```

请求字段：

- `query`
- `search_method`: `hybrid`、`dense`、`sparse`
- `top_k`
- `fetch_k`
- `min_score`

返回字段：

- `query`
- `search_method`
- `top_k`
- `fetch_k`
- `min_score`
- `hits[]`

前端使用场景：

- 调试召回质量。
- 对比不同检索模式。
- 查看 rerank metadata。
- 为回答页的引用展示提供透明依据。

### 5.6 回答生成

```text
POST /answer
```

请求字段：

- `query`
- `top_k`

返回字段：

- `query`
- `answer`
- `fallback`
- `citations[]`

前端展示规则：

- `fallback=false`：展示正式回答和引用。
- `fallback=true`：突出显示安全降级回答，不渲染为确定性诊断结论。
- `citations[]` 为空时不显示来源列表，但保留“未检索到可引用依据”的状态。

## 6. 组件设计

### 6.1 问答组件

- `QuestionForm`：问题输入、`top_k`、检索模式切换。
- `AnswerPanel`：回答正文、fallback 状态、响应耗时。
- `CitationList`：引用卡片列表，展示分数、`doc_id`、命中文本摘要。
- `CitationDetail`：点击引用后展开完整内容和 metadata。
- `SessionHistory`：当前会话的问题列表和快速回填。

### 6.2 管理组件

- `AdminLoginForm`：账号、密码输入和登录失败提示。
- `AdminEntryLink`：问答页中的受控管理入口，未认证时跳到登录页。
- `HealthBadge`：系统健康状态。
- `IngestForm`：导入参数表单。
- `IngestRunCard`：`ingest_run_id`、源路径、当前状态。
- `ProgressMeter`：百分比、扫描行数、ETA、速率。
- `BatchSummary`：成功、失败、待处理、跳过批次统计。
- `FailedBatchTable`：失败批次行区间、重试次数、错误信息。
- `CancelIngestButton`：运行中可用，终态禁用。

### 6.3 反馈状态

所有 htmx 提交都应覆盖以下状态：

- idle：可输入、可提交。
- loading：禁用重复提交，显示当前操作正在执行。
- success：替换目标片段。
- validation error：字段级或表单级提示。
- backend error：展示 HTTP 状态和可读错误。
- empty result：没有检索结果或没有失败批次时，展示明确空状态。

## 7. 状态管理

### 7.1 服务端状态

以下状态以服务端为准：

- 导入任务状态。
- 导入进度。
- 批次成功/失败信息。
- 检索结果。
- 生成回答。

前端不缓存这些状态作为最终事实，只负责展示最后一次服务端返回。

### 7.2 admin 会话状态

- admin 登录态以服务端可校验 cookie 为准，不依赖前端内存状态。
- 页面渲染时只需要知道“当前请求是否具备 admin 身份”，不需要把密码或明文身份注入模板。
- admin 会话失效后，导入管理页与入库 API 的行为必须保持一致，不允许出现“页面已退出但 API 还能调”或反过来的情况。

### 7.3 历史对话记录存储体系

当前问答页的历史对话记录不是浏览器本地临时状态，而是持久化到 MongoDB。

身份识别方式：

- 浏览器首次进入时提交昵称
- 服务端生成匿名 `user_token`
- `user_token` 通过 cookie 保存在当前浏览器
- 之后用 `user_token` 关联当前用户的历史会话

MongoDB 中的三组核心集合：

- `chat_profiles`
  - 保存 `user_token`、`nickname`、创建时间、更新时间
- `chat_conversations`
  - 保存 `conversation_id`、所属 `user_token`、标题、最近活跃时间
- `chat_messages`
  - 保存 `message_id`、所属 `conversation_id`、消息角色、正文、fallback 状态、引用列表、创建时间

当前持久化行为：

- 一个匿名用户可拥有多个会话线程
- 首次设置昵称后，系统会自动为该用户准备默认会话
- 每次提问都会写入两条消息：
  - 一条用户问题
  - 一条助手回答
- 助手回答会连同 `fallback` 和 `citations` 一起持久化
- 点击引用详情时，前端直接从已保存的 assistant message 中读取对应 citation，而不是重新发起 `/query`

这样设计的目的：

- 刷新页面后仍能恢复历史会话和消息
- 侧栏可以按最近活跃时间排序会话
- 回答引用可以长期回看，不依赖重新召回同一批结果
- 当前版本不需要用户登录系统也能拥有稳定的历史记录体验

## 8. 医疗安全展示原则

- 回答区不使用“确诊”“处方”“剂量建议”一类强化确定性的视觉标签。
- fallback 回答需要明显区别于正常回答。
- 引用内容必须可见，避免只有模型回答而没有依据。
- 涉及用药、手术、特殊人群、急症风险时，页面应保留就医提醒和安全提示位置。
- 前端不自行改写医学答案，只展示后端生成结果和引用依据。

## 9. 错误处理

| 场景 | 前端行为 |
|------|----------|
| 未登录或 admin 会话失效访问管理页 | 重定向到 admin 登录页，并保留 `next` 返回目标 |
| 未登录或 admin 会话失效调用入库 API | 页面层提示重新登录；JSON API 返回 `401` |
| 未导入数据时调用 `/query` 或 `/answer` | 展示“请先完成数据导入”的状态 |
| MongoDB 不可用 | 禁用导入提交，允许问答页继续尝试已有索引查询 |
| Milvus 不可用 | 问答结果区展示检索服务不可用 |
| 导入租约冲突 `409` | 展示已有任务正在运行，并引导查看当前 run |
| SSE 中断 | 保留最后状态，允许手动刷新 |
| 任务终态为 `completed_with_errors` | 展示失败批次明细，不当作完全成功 |

## 10. 性能与体验目标

- 问答提交后立即进入 loading 状态，避免重复提交。
- RAG 检索响应目标为 3 秒内，回答响应目标为 15 秒以内。
- 导入进度通过 SSE 推送，避免前端高频轮询。
- 引用详情按需展开，避免一次性渲染过长文本。
- 页面首屏不依赖大型前端 bundle。

## 11. 测试策略

### 11.1 单元与集成测试

- Web 路由能正确渲染页面和片段。
- admin 登录、登出、未登录重定向和失效会话处理正确。
- htmx 表单错误能返回可读 HTML 片段。
- API 响应能正确转换为模板 view model。
- 导入状态字段缺失或为空时，页面不崩溃。
- `/ingest` 相关 API 未认证时返回 `401`，已认证时保持现有行为。

### 11.2 浏览器验收

- 问答页可以提交问题并看到回答。
- 引用可以点击展开。
- 检索模式、`top_k` 能影响请求参数。
- 从问答页点击“导入工作台”时，未认证会进入 admin 登录页。
- admin 登录后可以进入导入管理页；登出后再次访问会被拦截。
- 管理页可以提交导入任务。
- 导入任务可以看到实时进度。
- 运行中任务可以取消。
- `completed_with_errors` 能看到失败批次详情。

## 12. 推荐开发顺序

1. 建立 `app/web` 目录、模板基类、静态资源挂载和 `/ui` 首页。
2. 完成问答表单和 `/ui/answer` htmx 片段。
3. 完成引用列表与引用详情展开。
4. 完成会话历史的浏览器端最小实现。
5. 完成 admin 登录页、admin cookie 校验和管理入口跳转。
6. 完成管理页导入表单和导入任务卡片。
7. 接入 SSE 导入进度更新。
8. 完成取消任务、失败批次表格和错误状态。
9. 为 `/ingest` 相关 JSON API 接入同一套 admin 鉴权。
10. 补充 Web 路由测试与浏览器验收脚本。

## 13. 验收标准

第二阶段完成时，至少应满足：

1. 用户可以从页面输入中文医疗问题并获得 RAG 回答。
2. 页面能展示引用来源，并支持查看命中文档内容。
3. 页面能识别并展示 fallback 安全降级状态。
4. 问答页中的导入入口受 admin 认证控制，未认证访问会被拦截。
5. 管理员可以通过页面提交数据导入任务。
6. 页面能实时展示导入进度、速率、ETA 和终态。
7. 页面能展示失败批次明细，并支持取消运行中的任务。
8. 前端不绕过现有后端状态机、幂等机制和 admin 鉴权边界。
9. Web 路由、模板片段和关键交互有基础测试覆盖。
