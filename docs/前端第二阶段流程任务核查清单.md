# 前端第二阶段流程任务核查清单

本文档参考《数据导入与检索生成全流程核查清单》的结构，面向第二阶段前端开发。状态标记建议：

- ⬜ 待完成
- ✅ 已完成
- ⚠️ 需确认

---

## 一、通用流程记录核查项

✅ 明确第二阶段前端范围：问答工作区、引用查看、会话管理、数据导入管理。

✅ 明确前端技术栈采用 `jinja2 + htmx`，不引入独立 SPA 构建链路。

✅ 明确页面层只做展示和交互编排，核心 RAG、导入、检索、生成逻辑仍由后端模块负责。

✅ 明确数据导入和管理能力需要简单 admin 认证，且与问答页匿名会话解耦。

✅ 明确所有前端页面使用当前后端 API 契约，不重复设计一套并行业务流程。

✅ 统一页面错误展示规则，包括 `400`、`401`、`409`、`503`、空结果、SSE 中断和任务失败。

⬜ 记录关键用户操作：提交问题、查看引用、提交导入、取消导入、查看失败批次。

---

## 二、app/web 模块核查项（前端页面层）

### 模块核心职责

⬜ 新增 `app/web` 前端页面模块。

⬜ 新增 Jinja2 模板目录和静态资源目录。

⬜ 提供问答工作区页面。

✅ 提供 admin 登录页面。

✅ 提供数据导入管理页面。

✅ 提供 htmx HTML 片段路由。

⬜ 将 API 响应转换为适合模板展示的 view model。

### 模块技术要求

✅ 页面路由与 JSON API 路由保持分离。

✅ htmx 片段接口返回 HTML，不直接把原始 JSON 丢给用户。

✅ 静态资源通过 FastAPI 正确挂载。

✅ 模板中对空字段、缺失 metadata、空 citations 做容错。

✅ `app/web` 提供统一的 admin cookie 校验、重定向和失效处理。

✅ Web 层不直接操作 Milvus、MongoDB 或模型 API。

---

## 三、问答入口核查项（用户主流程）

### 核心职责

✅ 页面提供中文问题输入框作为 RAG 搜索主入口。

⬜ 支持用户设置 `top_k`。

⬜ 支持选择检索模式：`hybrid`、`dense`、`sparse`。

✅ 提交问题后调用回答生成流程。

✅ 展示生成答案正文。

✅ 展示回答是否为 fallback 安全降级结果。

✅ 展示引用数量和引用列表。

✅ 问答页提供“导入工作台”入口，但入口本身受 admin 认证控制。

### 技术要求

✅ 提交期间按钮禁用，避免重复请求。

✅ 后端返回异常时，回答区域显示可读错误。

✅ 无检索结果时，页面展示安全降级状态。

⬜ 回答内容不在前端二次改写医学结论。

⬜ 页面保留医疗安全提示和就医提醒展示位置。

---

## 四、检索结果与引用核查项

### 核心职责

⬜ 引用列表展示 `doc_id`。

⬜ 引用列表展示 `score`。

⬜ 引用列表展示命中文本摘要。

⬜ 引用列表展示关键 metadata，例如 `source_path`、`source_line_no`、`retrieval_score`、`rerank_score`、`rerank_applied`。

✅ 点击引用后可以查看完整命中文本。

⬜ 支持查看不同检索模式下的命中差异。

### 技术要求

⬜ 过长引用内容默认折叠或按需展开。

✅ metadata 缺失时页面不报错。

⬜ rerank 未开启时，不展示误导性的 rerank 分数。

⬜ `score` 含义随 rerank 状态变化时，页面文案保持谨慎。

---

## 五、会话管理核查项

### 核心职责

✅ 支持当前浏览器会话内保存历史问题。

⬜ 支持点击历史问题快速回填或重新提问。

⬜ 支持显示历史回答摘要。

✅ 支持按当前实现展示和切换历史会话。

### 技术要求

✅ 当前实现中的会话历史与消息由服务端持久化到 MongoDB。

✅ 浏览器 cookie 中只保存匿名 `user_token`，不直接缓存完整历史内容作为事实来源。

✅ 问答匿名会话与 admin 登录态使用不同 cookie，不共享身份边界。

⬜ 前端不在本地额外持久化敏感医疗历史，除非后续有明确需求和脱敏方案。

---

## 六、数据导入管理核查项（管理员流程）

### 核心职责

✅ 管理页展示 `/health` 状态。

✅ 管理页突出展示 MongoDB 可用性。

✅ 未认证用户访问管理页时跳转到 admin 登录页，并保留返回地址。

✅ 提供 `source_path` 输入。

✅ 提供 `raw_batch_id`、`clean_batch_id`、`kb_batch_id` 可选输入。

✅ 提供 `flush_to_milvus` 开关。

✅ 提供 `force_reingest` 开关。

✅ 提交后展示 `ingest_run_id`。

✅ 提交后展示 `status_url`、`events_url`、`cancel_url` 对应操作。

### 技术要求

✅ MongoDB 不可用时禁用导入提交。

✅ admin 登录成功后才能发起导入、查看导入状态和取消导入。

✅ `409` 租约冲突时展示同目标导入正在运行。

✅ `400` 路径错误时展示源文件路径问题。

✅ `401` 会话失效时引导重新登录，而不是静默失败。

✅ `503` 基础服务不可用时展示服务不可用原因。

✅ 表单提交成功后立即进入进度跟踪状态。

---

## 七、导入进度与 SSE 核查项

### 核心职责

✅ 前端连接 `GET /ingest/{ingest_run_id}/events`。

⬜ 首次连接后展示当前快照。

✅ 接收 `progress` 事件并刷新页面进度。

✅ 展示 `stage`。

✅ 展示 `status`。

✅ 展示 `progress_percent`。

✅ 展示 `current_scanned_line / total_lines`。

✅ 展示 `processed_batches` 和 `skipped_succeeded_batches`。

✅ 展示 `lines_per_second`、`batches_per_second`、`eta_seconds`。

✅ 终态后关闭 SSE 连接。

### 技术要求

✅ SSE 中断时保留最后一次状态。

✅ SSE 中断后允许手动刷新状态。

⬜ heartbeat 不应误判为进度更新。

✅ `completed_with_errors` 不应展示为完全成功。

⬜ `failed` 状态应展示失败原因和失败批次。

---

## 八、取消导入核查项

### 核心职责

✅ 运行中任务展示取消按钮。

✅ 点击取消调用 `DELETE /ingest/{ingest_run_id}`。

✅ 取消请求发出后展示 `cancelling` 状态。

⬜ 取消过程中禁用重复取消。

✅ 最终展示 `cancelled` 状态。

### 技术要求

✅ 前端文案体现取消是协作式取消，不承诺立刻中断当前批次。

✅ 终态任务不展示可用取消按钮。

⬜ 取消失败时保留原任务状态并展示错误。

---

## 九、失败批次核查项

### 核心职责

✅ 展示 `failed_batches` 总数。

✅ 展示 `failed_batch_details[]`。

✅ 每条失败批次展示 `batch_id`。

✅ 每条失败批次展示 `start_line`、`end_line`。

✅ 每条失败批次展示 `attempt_count`。

✅ 每条失败批次展示 `error`。

✅ 支持失败批次为空时的空状态。

### 技术要求

⬜ 错误信息过长时折叠展示。

⬜ 前端不手工修改批次状态。

⬜ 补导失败批次仍通过再次调用普通 `/ingest` 完成。

---

## 十、API 集成核查项

### 必接 API

⬜ `GET /health`

⬜ `POST /answer`

⬜ `POST /query`

✅ `GET /ui/admin/login`

✅ `POST /ui/admin/login`

✅ `POST /ui/admin/logout`

✅ `POST /ingest`

✅ `GET /ingest/status?ingest_run_id=...`

✅ `GET /ingest/{ingest_run_id}/events`

✅ `DELETE /ingest/{ingest_run_id}`

### 契约要求

✅ 前端请求字段与 Pydantic 模型保持一致。

✅ 前端处理 `fallback` 字段。

✅ 前端处理 `citations[]` 为空。

✅ 前端处理 `exists=false` 的导入状态响应。

✅ 前端处理入库相关接口返回的 `401` 未认证状态。

✅ 前端处理导入终态：`cancelled`、`completed`、`completed_with_errors`、`failed`。

✅ 前端不依赖后端未承诺的内部字段。

---

## 十一、前端体验核查项

✅ 首屏直接进入可用问答界面，不做营销式首页。

✅ 医疗问答结果布局清晰区分“回答”和“依据”。

✅ 管理页以任务状态和操作效率为主，不做过度装饰。

⬜ 移动端输入、提交、查看引用不发生布局重叠。

✅ 所有按钮和输入控件具备清晰 loading、disabled、error 状态。

✅ 长文本、长路径、长错误信息不会撑破布局。

✅ 关键操作有明确反馈，不让用户猜测请求是否已提交。

✅ admin 登录页、管理页、问答页之间的跳转路径清晰，不让用户困惑自己当前是否具备管理权限。

## 十二、测试与验收核查项

### 自动化测试

✅ Web 页面路由返回 200。

✅ htmx 片段路由返回可渲染 HTML。

✅ `/ui/admin/login` 能处理正常登录、错误密码和已登录跳转。

✅ 未登录访问 `/ui/admin/*` 会被重定向到登录页。

✅ `/ui/conversations/{conversation_id}/ask` 能处理正常回答。

✅ `/ui/conversations/{conversation_id}/ask` 能处理 fallback 回答。

✅ `/ui/admin/ingest` 能处理导入提交成功。

✅ `/ui/admin/ingest` 能处理 `401`、`409`、`503`、`400` 错误。

✅ 导入状态 view model 能处理空字段和终态。

### 浏览器验收

✅ 用户可以输入中文医疗问题并看到回答。

✅ 用户可以点击引用查看命中文档。

⬜ 用户可以切换检索模式。

✅ 用户可以看到当前会话历史。

✅ 用户从问答页点击导入入口时，未登录会进入 admin 登录页。

✅ 管理员可以提交导入任务。

✅ 管理员可以看到实时导入进度。

✅ 管理员可以取消运行中的导入任务。

✅ 管理员可以看到失败批次详情。

✅ 管理员登出后再次访问管理页会重新要求认证。
